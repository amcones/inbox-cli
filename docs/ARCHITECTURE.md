# 是否需要交互式进程与内存滑动窗口

状态：评估提案，未实现。基线：v0.3.0；2026-09-30 本地复测。本文不授权架构改动。

## 结论

当前不必将整个项目重构为常驻进程。保留一次调用执行一条命令的默认方式；先定位全库扫描的成本，再根据连续使用需求决定是否增加可选 `inbox shell`。后台 daemon 应在确有跨调用缓存需求时另行评估。

用户担心的增长问题确实存在，但“每次读取文件”不能直接推导为“磁盘 I/O 已是主要瓶颈”。现有热缓存测试包含进程启动、目录枚举、Markdown/JSON 解析、字符串转换、排序、浏览日志回放，以及写操作的同步。它没有分离 CPU 与物理磁盘成本。

## 当前证据

本次复测在 macOS ARM64、优化构建、OS 热文件缓存下进行。每组预热 5 次，采样 30 次；每次启动新进程，保留写入同步，输出不包含终端绘制。完整环境、P95 和 RSS 见 [BENCHMARK.md](BENCHMARK.md)。下表为中位数，单位 ms。

| 操作 | 1,000 条 | 10,000 条 | 100,000 条 |
|---|---:|---:|---:|
| 新增 | 8.46 | 9.01 | 8.99 |
| 最近 20 条 | 3.12 | 3.19 | 4.84 |
| 全文搜索无结果 | 5.06 | 24.11 | 211.61 |
| 优先级 Top-20 | 4.47 | 18.85 | 167.07 |
| 查看并计数 | 9.10 | 21.39 | 147.66 |

新增只检查当前文件最多 256 字节尾部并追加，不扫描历史，数据增长没有明显影响该路径。最近列表能提早停止正文扫描，但仍枚举日期目录。普通搜索命中足够多的近期记录时也能提前停止；无结果或稀疏命中必须扫描全部正文。优先级回放浏览日志并扫描所有记录；ID 查找也扫描全库，以检测歧义和重复 ID。

这说明应优先研究全库扫描路径，而不是为了新增速度更换运行方式。以上测量不能证明冷盘、云盘、Windows 或 Linux 上有相同性能；也未测量缓存方案本身的收益。

## 三条路线的区别

| 路线 | 能解决的问题 | 代价与限制 | 当前判断 |
|---|---|---|---|
| 保留 CLI，优化扫描/可重建索引 | 所有调用中的 ID 查找、日志回放等重复工作 | 索引失效、兼容、重建与外部编辑检测 | 优先研究，先 profile 再决定是否加索引 |
| 可选交互式会话 `inbox shell` | 同一会话连续查询，避免反复启动和解析近期内容 | 首次加载、缓存一致性、会话内存及交互设计 | 有连续使用需求时可做原型 |
| CLI 连接后台 daemon | 不同调用共享内存缓存 | IPC、服务生命周期、崩溃恢复、升级、跨平台安装、后台资源 | 暂不需要 |

交互式会话退出后内存就消失；继续每次单独执行 `inbox ...` 并不会因此加速。要跨调用共享缓存，需要 daemon 或磁盘索引，两者是不同的产品与工程决策。

## 如果做滑动窗口，必须保留全库语义

建议原型使用“最近记录窗口 + 字节上限 + 按需加载”，例如最多 2,000 条、正文与缓存结构合计预算 16 MiB；这些是待验证的初始值，不是已承诺的指标。单条正文允许 1 MiB，仅按条数或天数限制不能控制内存。要测实际 RSS，考虑分配器及元数据开销。

- 最近列表先查窗口；需要更早记录时按日期加载并逐出冷数据。超大当天文件不能导致窗口无限增长。
- 全文搜索默认仍覆盖全库。窗口外回退扫描；如以后增加“仅近期”模式，应显式选择，不能偷偷漏掉旧记录。
- 全库 ID 前缀歧义检测必须保留。只在窗口命中一个 ID 不足以证明它唯一。
- 优先级不是按年龄单调递减：旧但常被查看的记录可能排在前面。只排序近期窗口会产生错误结果；必须维护覆盖全库的排名元数据，或回退完整扫描。时间流逝也会改变分数，不能永久缓存排序结果。
- 窗口对无结果搜索帮助有限；一旦回退全库，仍有磁盘读取/解析成本。缓存不能代替索引。

## 一致性与持久化要求

Markdown 保持权威数据源，内存及未来磁盘索引均可丢弃重建。启动时先完成已提交的删除恢复，再加载缓存。写操作在独占锁内落盘并同步成功后更新缓存；不能为了低延迟只写内存或延迟确认持久化。

交互式进程不能在等用户输入时一直持锁。每条命令分别获得相应锁，允许其他 CLI 进程工作。应用写入可配合库修订号使缓存失效；外部编辑不会更新该修订号，仍需重新核对文件集合与签名。仅依赖文件时间/大小可能漏掉同尺寸或时间被保留的修改，文件监听事件也可能丢失；若无法证明缓存新鲜，应回退重读，并保留显式刷新与完整检查。任何有损坏或恢复失败的状态都不能继续展示“看起来正常”的旧缓存。

删除、编辑、恢复、永久清空都要更新或使相关缓存失效。删除确认仍使用快照；恢复保持原 ID 和时间，历史浏览次数仍不恢复。缓存不能绕过这些既有语义。

## 建议的推进顺序与决策门槛

1. **补成本拆分**：分别测进程空启动、目录枚举、文件读入、Markdown/JSON 解析、正文小写转换、日志回放、排序与 `fsync`。增加冷缓存/慢存储、不同正文大小、集中在一天的大文件、稀疏搜索和大浏览日志场景；在五个平台上采样。
2. **先试有针对性的优化**：减少重复分配与解析；评估可重建的 ID/文件定位表和浏览计数检查点。索引需要验证文件变化、保留重复 ID 检查，并在丢失或陈旧时安全重建。全文检索索引另行测量体积、内存和维护成本。
3. **需要时做可选会话原型**：对比“现有 CLI”“CLI 加索引”“会话加窗口”在同一工作负载下的首次响应、连续响应、内存、二进制体积和正确性，不先承诺全面重构。
4. **达到门槛才采用**：建议将目标设为参考机器 10 万条记录的近期/ID 查询 P95 < 50 ms、无结果搜索 P95 < 100 ms；缓存路径相对基线至少快 2 倍，同时保持新增 P95 不明显回退。这些是建议的评审目标，不是当前性能保证。还应确认用户确实经常在一个会话连续操作，并完成外部编辑、多进程、崩溃与恢复测试。

按当前产品定位，先解决大库的全库扫描更有价值。若未来主要体验变为连续浏览和整理，再增加交互式会话；默认快速捕获命令继续保留。
