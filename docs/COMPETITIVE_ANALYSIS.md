# `inbox` 竞品分析

状态：产品研究；2026-09-30。范围是个人灵感的捕捉、找回、整理与恢复，不比较价格、融资、市场份额或 AI 模型能力。资料均来自产品官方文档或官方项目仓库；功能和可用平台会变化，应在制定路线图前再次核对。

## 结论

`inbox` 不该试图成为另一个 flomo、Obsidian 或 Notion。它有一个清晰但窄的机会：为重视本地文件、终端工作流和极低捕捉摩擦的个人，提供“**一条命令记下，仍能可靠找回**”的灵感收件箱。

这个定位由三个当前能力共同支撑：按日保存且可人工阅读的 Markdown、针对正文和标签的检索、以及编辑、回收站与恢复构成的可逆生命周期。它比通用笔记工具少得多，也不应与团队知识库比协作与结构化能力。下一阶段的竞争重点应是“找回时更省脑力”和“本地数据更可信”，而不是扩张成全功能知识管理系统。

## 研究方法与边界

本研究使用 Exa 检索并阅读 11 个一手资料，分为四个工作流：快速捕捉（flomo、Drafts、Apple Notes）、本地知识库（Obsidian、Logseq、Joplin）、命令行纯文本工具（`zk`、`nb`），以及工作区/数据库（Notion）。下表只比较各产品公开说明中与本项目相关的能力；“缺口”是相对 `inbox` 的产品机会，不是对竞品质量的否定。

来源质量：除 `nb` 与 `zk` 的 GitHub 官方仓库外，均为产品公司或项目维护者的官方帮助文档，属于直接说明已发布能力的一手资料。它们天然带有推广目的，因此本文不以其宣称推断用户满意度、市场规模或性能。

## 市场分层

| 分层 | 用户要完成的事 | 代表产品 | 竞争规律 |
|---|---|---|---|
| 随手捕捉 | 在灵感消失前写下片段 | flomo、Drafts、Apple Notes | 输入入口越多越好，之后以回顾、筛选或动作承接 |
| 本地知识库 | 长期积累、链接和检索大量笔记 | Obsidian、Logseq、Joplin | 可扩展性、同步和复杂查询优先，学习与维护成本上升 |
| 命令行纯文本 | 在编辑器和脚本环境中维护可迁移笔记 | `zk`、`nb` | 文件主权与可编程性强，常以配置和功能广度换取简单性 |
| 团队工作区 | 将文档、数据、流程和多人协作放在同一处 | Notion | 数据库、权限、视图与协作优先，个人即时记录不是核心体验 |

`inbox` 位于第一层与第三层之间：它首先是个人的快速捕捉入口，其次才是一个可脚本化的本地档案。这个交界比“又一个 Markdown 笔记软件”更容易让目标用户理解。

## `inbox` 的差异化主张

建议将产品主张固定为：**“面向终端用户的本地灵感收件箱：瞬间写入、无需账号、普通 Markdown 可读、删错可恢复。”**

它不是“极简 Obsidian”，因为其核心单位是按时间流入的灵感而非可连接的知识页；也不是“CLI 版 flomo”，因为它不依赖云同步或多端输入入口。这个边界可以指导功能判断：

1. 新功能若让“捕捉、找回、修订、恢复”更快或更可靠，优先考虑。
2. 新功能若要求引入账户、服务端、插件运行时、富媒体库或复杂数据库模型，默认拒绝，除非产品定位明确改变。
3. 任何性能优化都不能让外部编辑的 Markdown 悄悄失效；文件始终是权威数据，缓存和索引必须可丢弃重建。

## 机会与优先级

### P0：把“回顾”做成可解释、可控的入口

当前隐藏优先级已经结合近期性和查看次数。下一步应先补一个明确的回顾命令或视图，例如 `inbox review`，输出少量候选并说明其被选中的简单原因（近期、少看、常看等，具体策略需先定义）。flomo 的产品闭环证明“捕捉后回看”是核心价值，而这项能力与现有数据模型直接相邻。[flomo 的官方说明](https://flomoapp.com/?language=en)明确将快速捕捉、定期回顾、标签与搜索串成同一流程。

验收指标应是：用户不需要记住 ID、日期或精确关键词，仍能在一次命令中重新遇到值得处理的灵感；同时保留 `list --sort priority` 的现有确定性行为，避免把不可解释的推荐替换为默认列表。

### P1：为大库检索建立证据，再决定可重建索引

100,000 条基准中，无结果全文搜索的中位数为 211.61 ms，优先级 Top-20 为 167.07 ms；这是产品瓶颈，而新增保持约 9 ms。详见项目的[架构评估](ARCHITECTURE.md)。`zk` 将全文索引作为其高级检索的基础，说明索引是成熟路径，但不能由此推导它适合 `inbox` 的每个工作负载。

建议按以下顺序验证：先拆分扫描、解析、排序与日志回放成本；再用真实库测试一个可丢弃、可重建的索引原型；最后比较它与可选交互式会话的首次/连续响应、内存、二进制体积和外部编辑一致性。默认 CLI 不应变成后台服务。这个判断与[现有架构评估](ARCHITECTURE.md)一致。

### P1：增强可迁移性与恢复信心

公开强调“文件属于用户”还不够；用户需要验证它。下一步可加入只读的 `inbox export`（不改变日文件格式）或 `inbox backup check`，检查备份目录是否包含 `.inbox` 元数据与回收站。先做检查与文档，再考虑自动备份或同步。Apple Notes、Joplin 和 Notion 都把导入/导出或恢复纳入产品路径；对 `inbox` 而言，差异化是让这些保障保持简单、离线且无需账户。

### P2：低成本输入集成，但保持单向

优先完善现有 stdin 契约和 shell 示例，例如剪贴板、编辑器、Raycast/Alfred 或 Git hook 的单向写入。它借鉴 Drafts 与 flomo 的“从用户所在处捕捉”，但不建立由应用托管的自动化平台。每项集成都应是独立脚本或文档配方，主二进制仍只负责可靠写入。

## 明确暂不做的能力

| 能力 | 暂缓原因 | 重新评估条件 |
|---|---|---|
| 云同步、账户与多人协作 | 需要服务端、冲突处理、隐私与运营能力，偏离本地单二进制定位。 | 用户研究证明跨设备是核心阻塞，且可定义不牺牲本地文件所有权的方案。 |
| 富文本、图片、扫描、音频 | 增加文件格式、索引和发布体积，不能直接提升文本灵感的捕捉/找回闭环。 | 文本用户的高频真实需求被量化，且存储与迁移格式先确定。 |
| 图谱、双向链接、复杂查询语言 | 会改变信息模型和学习成本，更适合知识库工具。 | 产品从“灵感收件箱”转向长期知识管理，且有明确使用场景。 |
| 常驻 daemon | 仅加速跨调用缓存，却引入 IPC、生命周期和一致性风险。 | 性能剖析与连续会话研究证明磁盘索引无法满足目标。 |

## 产品指标建议

不应以“功能数量”衡量进展。建议在不收集笔记内容的前提下，用本地可选诊断或用户访谈观察以下问题：

| 目标 | 可观察信号 |
|---|---|
| 捕捉够快 | 从想到执行 `inbox add` 的平均步骤数、失败/取消率、写入 P95 延迟。 |
| 找回够可靠 | 搜索后 `show`、编辑或恢复的完成率；用户是否仍依赖目录/手工 grep。 |
| 回顾有价值 | `review` 后打开或编辑的比例，以及同一条记录的重复无效曝光率。 |
| 本地承诺可信 | `doctor` 成功率、备份检查覆盖率、恢复任务成功率、外部编辑后的一致性缺陷。 |
| 保持轻量 | 发布二进制大小、空启动与常用命令 P95、依赖数量。 |

这些指标用于产品学习，不应默认上报用户内容或行为数据；默认离线产品应把隐私作为实现约束。

## 决策

未来一个小版本建议只推进两件事：先完成 `review` 的产品定义与可用性测试，再为 10 万条以上库的检索做可重建索引的基准原型。两者都直接强化 `inbox` 的承诺，也不会把项目拖入通用笔记、团队协作或常驻服务的竞争战场。
